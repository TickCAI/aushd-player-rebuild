# 阶段1：签名配置热更改动记录

> 属于《下一阶段开发方案-热更弹幕账号挂载.md》的阶段1。目标：在不发新包的前提下，由分发服务下发一份**带签名的配置**，即时调整首页行顺序、功能开关、公告等；任何网络/签名/解析失败都静默降级为客户端内置行为。

## 一、背景与边界

- 这是**配置/资源热更**，不是 Dart 代码热更。下发内容只有数据（首页行顺序、featureFlags、公告、弹幕源、OpenList 预设），不含可执行代码。
- 账号正交：本次不涉及登录，不改 `isSignedIn`（媒体服务器登录语义）。
- 无分发服务（`AUSHD_DIST_URL` 为空，CI build-only 模式）时，`ConfigService.available == false`，四功能全部静默休眠，不请求任何占位域名。
- 签名用 HMAC-SHA256，服务端 `CONFIG_SIGNING_KEY`（缺省回退 `ADMIN_TOKEN`，再回退 dev key）与客户端 dart-define `AUSHD_CONFIG_KEY` 必须一致。

## 二、服务端改动（`server/`）

### `server/src/server.js`
- 新增配置键 `cfg.configKey = process.env.CONFIG_SIGNING_KEY || process.env.ADMIN_TOKEN || 'aushd-dev-config-key'`（真实部署必须设其一）。
- 新增 `DEFAULT_CONFIG = {version:0, homeRows:null, featureFlags:{}, announcements:[], danmakuSources:[], openlistPresets:[]}`。
- 新增 helper：
  - `allConfigs()`：读 `config.json` 的 scope→doc map。
  - `resolveConfig(platform, channel)`：`'*'` 为基线，叠加 `'platform:channel'` 或 `'platform'` 覆盖；`featureFlags` 深合并，数组字段整体覆盖。
  - `canonicalConfig(doc)`：递归按 key 排序后 `JSON.stringify`，剔除 `signature`，作为 HMAC 载荷。
  - `signConfig(doc)` / `configResponse(platform, channel)`：生成 `signature` 字段。
- 新增 3 条路由：
  - `GET /api/config?platform&channel&tag`：校验 platform/channel；无配置→204；`tag` 等于当前 version→204（省流量）；否则 200 返回带签名的配置。
  - `POST /api/admin/config`（Bearer）：upsert 指定 scope 的配置，校验 version 非负、homeRows 为数组，返回签名。
  - `GET /api/admin/config`（Bearer）：列出所有 scope 的配置。

### 测试与自检
- `server/test/smoke.js`：新增 14 条 config 用例（缺省 204、坏 platform 400、鉴权 401、upsert、签名正确、version/homeRows、flags 深合并、公告、tag 204、平台覆盖、覆盖 version、覆盖保留默认 rows、覆盖 flags 合并、admin list）。本地 `npm test` **33/33 通过**（Node v20.16.0）。
- `server/scripts/check-deploy.js`：新增 `/api/config` 自检（204/404 正常，200 必须带 signature）。

## 三、客户端改动（`lib/`）

### 新增 `lib/services/config_remote/`
- `remote_config.dart`
  - `RemoteConfig` 模型：version / homeRows / featureFlags / announcements / danmakuSources / openlistPresets / signature；`feature(key,{fallback})`。
  - `parse()`：校验 version≥0；**配置 key 非空时必须带合法签名**（防止攻击者直接删掉 `signature` 字段绕过验签）；解析各字段。
  - `verifySignature()`：对**原始 body** 剔除 `signature` 后递归 key 排序 + `jsonEncode`，用 Hmac(sha256, key) 比对，与服务端 `canonicalConfig` 字节级一致。
- `config_service.dart`
  - 构造：`baseUrl / channel / signingKey / platform（自动探测）/ ttl(30min)`。
  - `loadCached()`：启动时读磁盘缓存，验签通过才进入内存。
  - `refresh({force})`：GET `/api/config?platform&channel&tag=appliedVersion`，15s 超时；204/404 只 touch；200 验签通过且 version 不倒退才落盘；全程 try/catch 静默失败。
  - `applyRowOrder(rows, idOf)`：按远端 homeRows 顺序排列已知 id，**未列出的 id 原样追加**（部分配置不会误隐藏整块区域），未知 id 忽略。

### 接入
- `lib/app/release.dart`：新增 `AUSHD_CONFIG_KEY` dart-define（默认 dev key，须匹配服务端）。
- `lib/app/app_services.dart`：构造 `ConfigService`（无 DIST_URL 时 baseUrl 为空）；启动时 `loadCached()` 后后台 `refreshConfig()`；版本变化才 `notifyListeners()`。
- `lib/ui/pages/home_page.dart`：`_Row` 加稳定 `id`；`_buildRows` 给 11 行分配 id（continueWatching/myLibraries/thisWeek/homeTrending/homePopularShows/fresh/gems/myList/yourFavorites/smartPicks/recommendedForYou），末尾 `applyRowOrder`；`_onServices` 同时监听集合 key 与 configVersion，使异步到达的热更配置能重建行序。

### 测试
- 新增 `test/config_remote_test.dart`：`signedBody()` 用 Hmac 模拟服务端签名；RemoteConfig.parse 5 用例（正确签名/篡改拒绝/错 key 拒绝/空 key dev 放行/负 version 拒绝）；ConfigService.applyRowOrder 4 用例（无配置原序/重排+未列出追加/未知 id 忽略/篡改缓存不应用）；`_MemoryStore implements LocalStore`。

## 五、诚实边界

- 云端 CI 只验证编译/单测/构建，不接真实分发服务；签名链路的真机端到端需配置 DIST_URL + 一致 key 后验收。
- 热更只能调整**已有的**首页行 id 顺序，不能凭空新增行类型（新增 UI 仍需发版）。
- HMAC 密钥为共享对称密钥，客户端内置即视为公开；此机制防的是"篡改/误配置"，不是针对逆向用户的强鉴权。
- 签名依赖服务端 canonical JSON 与客户端 key 排序一致；两端算法已对齐并有单测覆盖，但任何一端改动排序规则都需同步。

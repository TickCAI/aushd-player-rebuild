# M3 · 渲染路径与生命周期

M3 处理的是《全屏崩溃-解决方案v1》里剩下的四条「让故障不可归因、让修复无效」的问题，
以及一条默认路径的纠正。它们都不是崩溃点本身，而是**让每一次崩溃都变成无头案**的原因。

| # | 问题 | M3 的做法 |
|---|---|---|
| 1 | `_play()` 被 `unawaited`，关停后仍继续 `load`/`selectTrack`，被 `MpvPlayer._disposed` 静默吞掉 | 引入播放代数（`_playGen`），过期调用**具名放弃并写日志** |
| 2 | OSD 相位变化就 `ShowWindow(SW_HIDE)`/`show()` 视频宿主 | 可见性只跟随「有没有帧」，不再跟随字幕/OSD 状态 |
| 3 | RenderGuard 把 `gpuApi` 直接写进用户配置，并把任何崩溃都当渲染问题降档 | 改成**模式记忆**：只避开死掉的那一种组合，不改用户选择 |
| 4 | `test/` 里没有任何窗口/全屏生命周期测试 | `FullscreenController` 7 个单测进 CI 闸门 |

---

## 0. 一句话结论

前三个版本修不好，有一部分原因不是修错了地方，而是**修完看不出有没有修对**：
关停之后仍在跑的播放任务被静默吞掉、视频宿主被 OSD 状态反复显示隐藏、
渲染后端被一个只有 20 秒记忆的守卫悄悄改掉。M3 把这三条都改成**有名字、有日志、有断言**。

---

## 1. 四项改造

### 1.1 播放代数：把「静默 no-op」变成「具名放弃」

改造前 `lib/playback/playback_session.dart` 的 `_play()` 是 `unawaited(...)` 出来的，
`_finishing` 只在某一处被检查一次。于是这条时序真实存在：

```
用户按 ESC → OSD 'back' → _finish() 开始拆播放器
                        ↘ _play() 还在 4.6s 的 HDR 等待里（waitForHdr 4s + 600ms）
                          → 继续 _player.load() / selectTrack() / _showVideo(true)
                          → 撞上 MpvPlayer._disposed 守卫，全部变成静默 no-op
```

结果是：**没有任何日志**能说明「这次会话其实是自杀的」，用户看到的是"退出时黑一下/卡一下"。

改法：

- 新增 `int _playGen = 0;`，`_play()` 开头 `final gen = ++_playGen;`，`_finish()` 里 `_playGen++`。
- 新增 `bool _abandoned(int gen, String where)`：发现 `gen != _playGen || _finishing` 时写
  `[session] play abandoned at <where> (gen=.. current=.. finishing=..)` 并返回 true。
- 三个守卫点：`playback info`（首次 `getPlaybackInfo` 之后）、`hdr`（原 `if (_finishing) return;`）、
  `load`（`_player.load()` 之前）。catch 分支里超期的失败不再弹错误卡。

为什么不是「把 `_finish` 置为 await」：`_finish` 由 ESC→OSD `'back'` 的同步路径触发，
把它 await 会把 UI 线程挂在 mpv 的关停链上（M2 刚把那条链做长）。**放弃**比**阻塞**安全，
但放弃必须留名。

### 1.2 OSD 相位不再决定视频宿主的可见性

改造前 `lib/playback/mpv/mpv_backend.dart`：

```dart
_showVideo(_curtain.phase == 'playing' && _framed);
```

这句话的意思是：只要 OSD 进入非 `playing` 相位（加载、暂停面板、字幕选择……），
就把承载 mpv 的子窗口 `ShowWindow(SW_HIDE)`，回 `playing` 再显示回来。
Windows 上隐藏/显示一个 `--wid` 嵌入的 mpv 渲染窗口 = **销毁并重建交换链**。
1.0.9 花力气去掉了 `SWP_FRAMECHANGED`（我在 §1.2 的反证里说明那是误读），
真正每几分钟就来一次的 frame churn 在这里。

改法：新增 `void _syncVideoWindow()`，内容只有 `unawaited(_showVideo(_framed));`，
`osd()` 与 `MpvPlaybackRestart` 两处都改调它。可见性现在只回答一个问题：
**当前有没有可显示的画面**。OSD 想画什么，由 mpv 自己在画面之上叠（`zerk_osd.lua` 本来就是 OSD 绘制方）。

### 1.3 RenderGuard：从「改用户设置」到「记住坏模式」

改造前的行为：只要上一次播放崩了，就把 `gpuApi` 往下一档写，**写进用户配置**，
且判据是 `markPlaybackFinished` 的 20 秒 Timer；换到 Windows 上，这个"降档"方向还是反的
（Vulkan 与 D3D11 走同一个 `amdxx64` 用户态驱动）。

改法（`lib/playback/render_guard.dart` 全量重写）：

| 能力 | 实现 |
|---|---|
| 模式指纹 | `fingerprint({vo, api, gpuContext, hwdec})` → `vo=gpu api=d3d11 context=d3d11 hwdec=d3d11va` |
| 记录 | `markPlaybackStarted({required String mode})`：`ending=true` + `mode` 落盘（在 mpv `create` **之前**调用） |
| 启动恢复 | `recoverOnStartup()`：`ending==true` → `_avoid = mode`，然后跑一次默认纠正 |
| 本次避开 | `resolveMpvMode(settings:, avoid:)`：指纹命中 → `nextApi()` 降一档、`avoided: true`，**只影响本次启动** |
| 连续成功 | `finishClean()`：3 次干净关停 → 清掉记忆（`cleanToForget = 3`） |
| 启动失败 | `noteLaunchFailure()`：mpv 起不来（无 ICD、坏上下文）→ 把这个模式标记为要避开 |
| 用户选择 | `migrateDefault()`：只纠正**从未手动选过**的安装（`gpuApiAuto == true`），手动选择一律不动 |

删除了 `fallback()` 与 `notePlaybackFailure()`。用户设置里不再有"程序自己改的 gpuApi"。

### 1.4 `FullscreenController` 单测（方案 §3.3 的 T3）

`test/fullscreen_controller_test.dart`，7 个用例，mock `MethodChannel('zerk/window')`：

1. `sync()` 采纳原生状态；
2. 请求与当前一致时不发 `setFullScreen`（不制造无意义 resize）；
3. 正常转换的相位与计数；
4. 原生拒绝时**以原生为准**并把 `failures` 加一；
5. `PlatformException` 记为失败而不是抛出；
6. 三次并发 `toggleFullScreen()` 必须串行（`transitions == 3`、`queued == 0`、最终 `fullscreen`）；
7. 排队中的请求能看到前一个的结果（不是各自读一次原生状态）。

这是仓库里第一次有测试真正覆盖"全屏"这条路径。

## 2. 默认渲染路径回到 `(gpu, d3d11, blt, d3d11va)`

`lib/playback/player_settings.dart` 默认值：

| 项 | 旧 | 新 | 依据 |
|---|---|---|---|
| `videoOutput` | `gpu-next` | `gpu` | 11:19 那份 dump 的渲染栈是 `vo/gpu-next` + libplacebo + amdvlk64 |
| `gpuApi` | `vulkan` | `d3d11` | 1.0.5 把默认改 Vulkan 的理由（"D3D11 崩了"）选错了变量：Vulkan 走同一个 `amdxx64` |
| `hwdec` | `auto-safe` | `d3d11va` | 与 d3d11 后端匹配；非 d3d11 后端仍自动退回 `auto-safe` |
| `d3d11-flip` | — | `no` | 只在 `api == d3d11` 时下发；flip-model 交换链正是全屏过渡时重建的那一个 |

`gpu-next` / Vulkan 仍然可选，只是不再是默认，也不再是"自动降级"的目标。

## 3. 云端证据

全部在 windows-latest 上跑，head 都在 `283777f` 之后。

### 3.1 编译与单测（`build.yml`）

| job | 结果 |
|---|---|
| Validate distribution config | ✓ |
| **Tests and compile gate**（analyze + `flutter test`） | ✓ 含 M3 新写的 7 个 `FullscreenController` 用例、重写的 3 个 GPU/守卫用例 |
| Build windows / androidtv / linux | ✓ |
| Publish release | ✓ |

这是仓库第一次让"全屏"这条路径进 CI 闸门。前三个版本改完之后，没有任何一条自动断言会失败。

### 3.2 全屏 soak（`window-soak.yml`，run `44229380861`）

| 指标 | 40 轮 | 200 轮 |
|---|---|---|
| `wmSize` / `transitions` | 131 / 88 | **659 / 440** |
| 比值（每次切换的 WM_SIZE 次数） | 1.49 | **1.50** |
| `mismatch`（原生与 Dart 状态不一致） | 0 | **0** |
| `moves` / `coalesced` / `minimizedResize` | 0 / 0 / 0 | 0 / 0 / 0 |
| 帧数 | 1487 | 7163（要求 ≥ 400） |
| 过渡期 `p99` | 31 ms | 32 ms |
| 过渡期 `worst` | 47 ms | **51 ms** |
| 帧预算（4× idle 中位数，下限 50 ms） | 50 ms | 79 ms |
| 结论 | `PASS iterations=40` | `PASS iterations=200` |

两点读法：

1. **比值不变**是最关键的一条：轮数翻五倍，每次切换产生的 `WM_SIZE` 次数仍是 1.5 次。
   「`WM_SIZE` → `MoveWindow` → 再 `WM_SIZE`」这条自激回路没有回来（M1 已闸住，M3 没有破坏它）。
2. **`worst` 从 234 ms 降到 51 ms**（同为 200 轮、同为 M1 之后的 harness）。跨 run 有环境噪声，
   不能当定理；但 M1 那次 200 轮的 234 ms 与用户生产日志里的 `[jank] 380 ms frame` 同量级，
   而这次没有复现出百毫秒级的停顿。

## 4. 云端没有证明的四条

1. **没有任何一次真实播放**。soak 不创建 video host、不加载文件，所以
   §1.2 的交换链抖动在云端**一次都没被触发过**——它只是不再被 OSD 相位驱动。
2. **§1.1 的放弃路径没有被执行**。soak 不进入 `PlaybackSession`，代数守卫的正确性靠代码推理与
   日志锚点的存在性，不靠观察。
3. **§1.3 的模式记忆只被单测覆盖**，没有被"真的崩一次再启动"验证过。
4. 托管 runner 没有 AMD GPU，也没有 libmpv：`amdxx64` 那次崩溃在云端**永远不可能复现**。

所以 M3 的云端绿灯含义只有一句：**这些改动没有让窗口层和编译回归**。
它不能、也不应该被读成"崩溃修好了"。

## 6. 需要真机做的一步（L3）

一次完整会话，四条一起看：

1. 30 分钟 4K HDR 播放 + 200 次全屏切换，**退出后没有新的 `*.dmp`、没有事件 1000/1001**；
2. 应用日志里关停链严格有序：`[session] finish` → `[mpv] quit sent` → `[mpv] shutdown event` →
   `[vo] uninit` → `[video_host] hidden` → `[refresh] restored` → `[hdr] restored` → `[session] close done`；
3. 若出现 `[session] play abandoned at ...`，它必须出现在 `[session] finish` **之后**（这证明放弃是对的，
   而不是又一次静默吞掉）；
4. 若曾经崩在某个模式上，下一次启动的 `[session] mode ...` 行必须带 `(avoided)`，
   且**用户设置里的 `gpuApi` 没有被改动**。

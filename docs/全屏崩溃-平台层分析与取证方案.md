# 全屏播放崩溃 —— Windows / 桌面平台层分析与取证方案

> 范围：`0xC0000005` 反复崩溃（播放中切入/切出全屏），AMD Radeon 780M + 200% DPI + 2880×1800 + 10 个 GameViewer 虚拟显示器 + Steam Vulkan 隐式层。
> 结论性质：**假设 + 判定实验 + 参数建议 + 取证方案**。本文不改代码。

---

## 0. 一句话结论

当前架构把 mpv 当成"别人的窗口"嵌进 Flutter 顶层窗口，并在**每次 WM_SIZE 时从 UI 线程直接 `MoveWindow` mpv 自己拥有的 VO 子窗口**（`windows/runner/video_host.cpp:135-143`）。全屏切换正是"窗口尺寸骤变"的最大来源，这一步会驱动 mpv 反复销毁/重建 swapchain（D3D11 `ResizeBuffers` / Vulkan `vkCreateSwapchainKHR`）。两份 dump 的签名（**execute @ `0x0`** 与 **read @ `0x24`**）都是"空对象解引用"的教科书形状，而不是驱动在随机地址炸掉 —— 这与"swapchain 重建失败后仍被使用"的代码路径高度吻合。

v1.0.9 的"去掉 `SWP_FRAMECHANGED`"没有消除 `WM_NCCALCSIZE`（见 §3.1），所以那次实验是混淆的：崩溃没消失**不能**用来否定"resize churn"这条线。

在拿到 `faulting module` 之前，一切归因都是猜测 —— 而拿到它只需要一条命令（§5.1）。

---

## 1. 平台层三处可疑点（带行号）

### 1.1 从 UI 线程直接改写 mpv 的窗口（最可疑）

`windows/runner/video_host.cpp:135-143`

```cpp
void VideoHost::OnParentResized() {
  if (!hwnd_) return;
  RECT rc;
  GetClientRect(parent_, &rc);
  MoveWindow(hwnd_, 0, 0, rc.right - rc.left, rc.bottom - rc.top, TRUE);
  if (HWND child = GetWindow(hwnd_, GW_CHILD)) {      // ← mpv 自己的 VO 窗口
    MoveWindow(child, 0, 0, rc.right - rc.left, rc.bottom - rc.top, TRUE);
  }
}
```

问题点：

1. **跨线程改别人的窗口。** mpv 的 win32 VO 窗口由 mpv 内部一条独立线程创建并跑消息循环（`video/out/w32_common.c` 的 window thread）。我们从 Flutter 平台线程对它发 `MoveWindow`，等价于跨线程 `SendMessage`：目标线程若正卡在 `Present`/驱动里，本线程阻塞；目标线程若正在销毁/重建自身的 swapchain，就可能踩到中间态。
2. **每次 WM_SIZE 都做两次 resize。** 全屏切换一次会产生**多次** WM_SIZE（GWL_STYLE 变化 → SetWindowPos → Flutter view resize → DWM 帧重算 → window_manager 的 `WM_GETMINMAXINFO` 参与重算）。也就是一次"切全屏"= 十几个 `ResizeBuffers`/`vkCreateSwapchainKHR`，**全在 100ms 内**。
3. **`bRepaint = TRUE`。** 强制给 mpv 的窗口投递 `InvalidateRect`+`WM_PAINT`。mpv 的 VO 用好几个 swapchain 出帧，不走 GDI 绘制；外部注入的 paint 对它没有意义，只是多一条重入路径。
4. **没有 `IsWindow` 保护、没有"mpv 当前是否已 configure vo"的判断。** mpv 在 `mpv_terminate_destroy` 期间销毁自己的窗口（`mpv_backend.close()` 的顺序是 `VideoHost.hide()` → `_mpv.dispose()`），这个窗口句柄在此期间是悬空的。

`printf` 式的旁证：`lib/playback/render_guard.dart:21-24` 的注释里已经记过一笔 —— "a crash in `vo/gpu-next/win32 uninit` happens after the user pressed back but before mpv is gone"。**VO 的 win32 生命周期路径已经被独立观察到过一次**。

### 1.2 全屏实现是"手改 GWL_STYLE"，并且刻意不发 FRAMECHANGED

`windows/runner/native_window.cpp`（`SetFullScreen`）：

```cpp
SetWindowLongPtr(window_, GWL_STYLE, saved_style_ & ~(WS_OVERLAPPEDWINDOW | WS_MAXIMIZE));
SetWindowPos(window_, HWND_TOP, rc.left, rc.top, w, h, SWP_NOOWNERZORDER);   // 无 SWP_FRAMECHANGED
```

3.1 节会说明：这并不能避免 `WM_NCCALCSIZE`。更要紧的是：**它和 `window_manager` 插件并存**。`window_manager-0.5.2` 通过 Flutter 官方的 `TopLevelWindowProcDelegate` 挂了一个窗口过程（`window_manager_plugin.cpp:135-230`），自己维护 `is_frameless_` / `title_bar_style_` / `pixel_ratio_` 状态，并在 `WM_NCCALCSIZE`、`WM_GETMINMAXINFO`、`WM_NCHITTEST` 上做决策。我们手改 `GWL_STYLE` 它完全不知道 → 两套状态机。今天默认配置（`title_bar_style_ == "normal"`、`is_frameless_ == false`）下它只是放行，**但这套"正常"是脆的**：任何人以后调用 `windowManager.setFullScreen(true)` 或 `setTitleBarStyle(hidden)`，NC 计算就会被插件接管，和我们的 `saved_style_` 打架。

顺带一个真实缺陷（不是崩溃，是功能）：不进 `SWP_FRAMECHANGED` 时边框消失依赖"随后的尺寸变化顺带触发 NCCALCSIZE"这个隐式行为。换窗口状态（比如进全屏前是最大化）时这个假设会破。

### 1.3 全屏切换是"两跳 IPC + 读-改-写"，没有串行化

`lib/core/windows/native_window.dart:24-28`

```dart
static Future<bool> toggleFullScreen() async {
  final fs = !(await isFullScreen());   // 跨 channel 读
  await setFullScreen(fs);              // 跨 channel 写
  return fs;
}
```

两个并发来源会打架：F11 在 `lib/main.dart:172` 绑了一份，OSD lua 里 `assets/mpv/zerk_osd.lua:1390/1472` 又绑了一份（`f`/`F11`/双击），两边最终都落到同一个 `_toggleFullscreen()`（`lib/playback/mpv/mpv_backend.dart:551-555`）。按键重复、双击、或"F11 + 点击"叠加时，`isFullScreen()` 的读和 `setFullScreen()` 的写可能交错 → 状态翻转错乱。这不是崩溃根因，但会污染复现记录（"我点了两次才切过去"）。

## 2. 根因假设（按可能性排序）

### H1 —— mpv swapchain 反复重建 → 失败路径上空对象解引用（最可能）

**机制链**：`WM_SIZE`风暴 → 我们对 mpv 的 VO 窗口暴力 MoveWindow → mpv `resize()` → `pl_swapchain_resize` / `ResizeBuffers`。4K HDR + 每帧 Present 中的 swapchain 在 AMD UMD 上可能返回 `DXGI_ERROR_INVALID_CALL`（backbuffer 仍被引用）/ `VK_ERROR_OUT_OF_DATE_KHR` / `VK_ERROR_SURFACE_LOST_KHR`。mpv/libplacebo 在失败路径上会留下 `swapchain == NULL` 或半初始化状态，后续 render 直接读字段 → **read @ 小偏移**（0x24 量级，与 `aushd-crash-20261117-130037` 完全对得上）；另一条路径上空函数指针被调用 → **execute @ 0x0**（与 `-111942` 对得上）。两份 dump 是同一个类的两个化身。

**支持**：
- 只在"播放中切全屏"崩；桌面/空播不崩。
- v1.0.11 把宿主从 `WS_CHILD` 换成 owned `WS_POPUP` 仍崩 → 说明不是"嵌入方式"的错，而是**"resize 事件到达 mpv"这条链**的错（owned popup 一样要跟随 resize）。
- 独立 `mpv.exe` 切 40 次不崩 → 关键差异不是"mpv 会不会处理 resize"，而是**"有没有第三方从别的线程去 resize 它的窗口"**。mpv 自己处理自己的 `WM_SIZE` 是单线程、同步、可控的；我们的外部 `MoveWindow` 不是。

**判定实验（不改代码，改设置）**：
- E1：4K HDR 片段，连续切 10 次全屏，`hwdec=no`（排除 DXVA/D3D11VA 纹理与渲染器共设备）。
- E2：同上，`gpu-api=d3d11, gpu-context=d3d11, d3d11-flip=no`（保守窗口化 swapchain）。
- E3：同上，`gpu-api=opengl, vo=gpu, gpu-context=win`（WGL，最老最稳）。若 E3 稳，则"窗口 resize 本身"无罪，罪在具体 context 的重建实现。
- 结论矩阵：只有 E3 稳 → 换渲染路径；E1/E2/E3 全崩 → 转 H2/H3（窗口/生命周期层）。

### H2 —— 跨线程 / 悬空窗口句柄（VO 生命周期竞争）

**机制**：mpv 在 VO 重建或 teardown 期间销毁自己的窗口，而我们的 `GetWindow(hwnd_, GW_CHILD)` 拿到的是旧句柄；或其 `GWLP_USERDATA`/`self` 已被释放，消息仍在投递 → handler 解引用已释放对象（读 @ 0x24 或调空 vtable）。
**支持**：`render_guard.dart` 注释里那条 `vo/gpu-next/win32 uninit`；`close()` 顺序把 mpv 的销毁放在宿主隐藏之后（窗口对象还在，子窗口正在消失）。
**反对**：用户复现是"播放中"切，不一定撞 teardown。
**一分钟判定**：给 `OnParentResized` 加一行 `IsWindow(child)` 检查 + 计数日志，看崩前是否出现 `child==NULL` / `IsWindow==FALSE`。或用 Spy++ 看 mpv VO 窗口的**线程 ID 是否等于本进程 UI 线程**（`GetWindowThreadProcessId`），一秒钟证伪"同线程自理"的直觉。

### H3 —— Flutter/ANGLE 侧的 swapchain resize

**机制**：Flutter Windows 用 ANGLE(D3D11) 出 UI；顶层窗口尺寸骤变时 engine 自己也要 `ResizeBuffers`。`flutter_window.cpp:60-67` 先调 `HandleTopLevelWindowProc`，再进我们的 `WM_SIZE`，时序上是我们先 resize mpv、后 resize Flutter view。
**支持**：两份崩溃签名也可能落在 `flutter_windows.dll` —— 现在**没人知道 `0x7FF863A4AA83` 属于哪个模块**（这正是 §5 要解决的第一件事）。
**判定（最便宜，建议第一个做）**：**不播视频，只反复切全屏 10 次**。崩 → H3/H1.2；不崩 → 与 mpv 强相关。

### H4 —— HDR / 显示器色彩模式切换叠加

**机制**：`_prepareHdr`（`lib/playback/playback_session.dart:856-872`）用 DisplayConfig 打开 Windows HDR；同时 `target-colorspace-hint=yes`（`lib/playback/mpv/mpv_options.dart:77`）让 mpv 也去申请 HDR swapchain（DXGI colorspace / VkColorSpace）。**两个 actor 同时改同一条输出管线**，再叠一次全屏 resize。
**判定**：`autoHdr=false` 或 `target-colorspace-hint=no` 跑同一复现；再单独测 SDR 4K。用户说"4K/HDR 更容易"，但也可能只是 4K 更吃显存/带宽，让 resize 更容易失败 —— 这两种解释要用实验分开。

### H5 —— 驱动 TDR / device removed

**机制**：真正的 device removed 会表现为 `DXGI_ERROR_DEVICE_REMOVED` + 系统事件 4101（`Display driver amdkmdag stopped responding`），**不是** AV。若确认是这条路，方向是"检测并重建"，而不是继续找空指针。
**判定**：`Get-WinEvent`（§5.2）+ PresentMon（§5.5）。若崩前有 4101，H5 成立，H1 的"失败路径"就变成了"驱动先挂了，mpv 没处理"。

### H6 —— 滚动 master 版 libmpv（横向混淆项，必须消除）

`.github/workflows/build.yml:141-167` 从 `shinchiro/mpv-winbuild-cmake` 的 **`releases/latest`** 取 `libmpv-2.dll`。也就是：**同一个 app 版本号，不同日期构建会装进不同的 mpv**。这足够解释"v1.0.8~v1.0.14 全部失败"——每次都在动渲染配置，而底座在漂。朋友机器也崩，但两人可能装着不同构建。
**判定**：读 `mpv-version`（`mpv_get_property_string("mpv-version")` 或日志头），对比两台机器、对比多个构建产物。
**修复方向**：pin 到一个 release tag / commit，并把该 commit 的 pdb 一起归档。

> 排序依据：H1 有机制、有签名吻合、有旁证；H6 是"必须消除的噪声"而不是根因；H3 成本最低应尽早排除；H5 是可观测的事实问题，靠日志一锤定音；H2 需要 instrument 才能判。

## 3. 两个需要纠正的既有判断

### 3.1 `SWP_FRAMECHANGED` 不是 `WM_NCCALCSIZE` 的开关

v1.0.9（commit `3203d5d`）的假设是"去掉 `SWP_FRAMECHANGED` 就避免了 NC 重算"。**不成立**：

- `WM_NCCALCSIZE` 由**窗口尺寸变化**触发（`SetWindowPos` 只要不是 `SWP_NOSIZE`，就会走 `WM_WINDOWPOSCHANGING → WM_NCCALCSIZE → WM_WINDOWPOSCHANGED`）。
- `SWP_FRAMECHANGED` 的作用是：**即使尺寸没变也强制重算一次** NC 区域。

进全屏用的正是"改尺寸"的 `SetWindowPos(w,h)`，所以 NC 重算照样发生；去掉 flag 只是少了一次冗余重算。**因此"崩溃仍在"无法证伪 churn 假设** —— 这个实验被污染了。真正要拿掉的 churn 是 §1.1 的外部 `MoveWindow`，而不是这个 flag。

### 3.2 `RenderGuard` 的降级顺序在 Windows 上是反的

`lib/playback/render_guard.dart:77-85`：第一次崩溃 → `gpuApi='vulkan'`（当作"更安全"）；第二次 → `opengl/gpu/hwdec=no`。
`migrateDefault`（71-74）还把"未动过的 d3d11 默认"迁到 vulkan。

但在 Windows 上，**D3D11 是唯一被百万级用户验证过的 mpv 输出路径**（VLC/mpv 默认、flip-model 有十年级别的兼容性打磨）；`gpu-context=winvk` 是 2024 才进 mpv 的新代码，而且 Vulkan 会吃到 Steam / Overwolf / RTSS 这类隐式层注入，D3D11 不会。把 vulkan 当"退路"是方向性错误。

另外一个副作用：`fallback` 会让**同一个 app 版本在不同机器/不同启动里跑不同的渲染路径**（第 16:55 的日志里 `VO: [gpu]` 就是被降级成 WGL 了），任何 dump 分析都必须先确认"这一跑到底走的哪条路"，否则会把两种完全不同的栈混在一起。

## 4. 渲染路径与参数建议

### 4.1 三套组合（按"成熟度"排，不是按"新特性"排）

| 组合 | vo | gpu-api | gpu-context | hwdec | 适用 | 代价 |
|---|---|---|---|---|---|---|
| **A 最保守** | `gpu` | `opengl` | `win` (WGL) | `no` | 只要不崩就行；老驱动/虚拟显示器/远程桌面 | 无 HDR 直通（tone-map）；4K60 软解吃 CPU |
| **B 推荐默认** | `gpu` | `d3d11` | `d3d11` | `d3d11va` | Windows 主力路径；HDR 直通可用；`d3d11-flip=no` | 老一代算法（非 gpu-next），部分高级 tone-mapping 缺失 |
| **C 现状/实验性** | `gpu-next` | `vulkan` | `winvk` | `auto-safe` | 追新特性 | Windows 上最不成熟；隐式层敏感；swapchain 重建路径新 |

**建议**：默认值改 B（`vo=gpu, gpu-api=d3d11, gpu-context=d3d11, d3d11-flip=no, hwdec=d3d11va`），把 C 在设置里标为"实验性（Windows 上可能不稳定）"。同时对 B 单独跑一次 §2 E2 复现，确认它真的不崩 —— 因为 v1.0.8 曾在 d3d11 上炸过（`amdxx64+0x124815`，属于 FRAMECHANGED 时代，需要重测）。

### 4.2 值得单独 A/B 的参数（每个都指向一个假设）

| 参数 | 试什么 | 验证什么 |
|---|---|---|
| `hwdec=no` / `d3d11va` / `auto-safe` | 三档 | 硬解纹理与渲染器共设备时，device 丢失是否被放大（H1/H5） |
| `video-sync=audio` + `interpolation=no` | 对比 `display-resample` | resample/interpolation 会在 resize 期间驱动特殊 Present 节奏（H1） |
| `d3d11-flip=no` | 开/关 | flip model 与 blt model 的 resize 失败率差异（H1） |
| `target-colorspace-hint=no` | 开/关 | HDR 直通是否参与（H4） |
| `--gpu-debug` | 开 | 拿 gpu/gpu-next 内部状态（取证用） |
| `VK_LOADER_LAYERS_DISABLE=~implicit~` | 环境变量 | Steam/Overwolf 隐式层是否参与（H1，先 `VK_LOADER_DEBUG=layer` 看清单再关） |
| `msg-level=all=v` | 覆盖现有 `msg-level=ffmpeg=error` | 现在 VO/gpu/vulkan 的日志被整体关掉了（`mpv_options.dart:60`），等于自断线索 |

### 4.3 结构性改动建议（属于代码，仅列出方向）

1. **resize 合并 + 保护**：`WM_SIZE` 里只记录目标尺寸，用 80–120ms 定时器或在 `WM_EXITSIZEMOVE` 时**合并成一次** resize；`MoveWindow(..., FALSE)`；`IsWindow(child)` 判空；mpv `vo-configured=no` 时直接跳过。
2. **全屏改用 `window_manager.setFullScreen()`**：它是 media_kit 同源实现（`window_manager.cpp:575-654` 的注释明确指向 media_kit 的 `utils.cc`），做法是 `SetAsFrameless()`（`DwmExtendFrameIntoClientArea` 负边距）+ `GWL_STYLE` 去掉 `WS_THICKFRAME|WS_MAXIMIZEBOX` + **两次** `SetWindowPos`（先定位后定尺寸，都带 `SWP_FRAMECHANGED`）+ 退出时**显式**重设 FlutterView 的尺寸。比自己手写可靠得多，也顺手解决了 §1.2 的"两套状态机"。
3. **`toggleFullScreen` 串行化**：一个 `_toggling` Future/mutex，避免读-改-写交错（§1.3）。
4. **不要再走 v1.0.11 的 owned popup 路线**：它证明"换嵌入方式"无效，因为 resize churn 依旧；只会在多窗口焦点/DPI 上引入新问题。

### 4.4 终局架构建议（值得排期，不是这一次的修复）

**放弃 HWND 嵌入，改用 `vo=libmpv` + `mpv_render_context`**，把画面渲进 Flutter 的纹理（media_kit 的做法：ANGLE EGL 上下文 + `MPV_RENDER_PARAM_OPENGL_FBO`，再经 Flutter 的 GPU surface / D3D11 shared handle 零拷贝给 engine；退化路径是 pixel buffer 拷贝）。

收益：全屏切换退化为"改一个 FBO/纹理的尺寸"，**完全不经过窗口系统和 swapchain 重建**，H1/H2/H3 三类一起消失；顺带解决 OSD 路由、多窗口、截图取帧。
成本可控的证据：`windows/runner/trailer_texture.cpp` 已经把 `mpv_render_context` 的 **sw** 路径跑通了（`kParamApiType="sw"`、三缓冲、`MarkExternalTextureFrameAvailable`），迁移是把 sw 换成 gl/d3d11 + 换像素搬运方式。
注意：sw 路径在 4K60 HDR 上不可接受（`trailer_texture.cpp:169-189` 每帧全屏 `rgba` CPU 转换 + 一次拷贝），只能用于小尺寸 trailer —— 这也解释了为什么它现在只在预告片里用。

## 5. 崩溃取证方案（怎么拿到"能定位"的 dump 和日志）

### 5.0 现状：仓库里根本没有崩溃处理器

`git log --all -S MiniDumpWriteDump` **全历史为空**。也就是说现有那几个 `.dmp` 只能来自 WER 或早期非本仓库版本。所以第一步不是写代码，而是**先用系统能力把 dump 抓下来**（零风险、立刻生效）。

### 5.1 【最高性价比，5 分钟】先确定 faulting module

```powershell
Get-WinEvent -LogName Application -FilterHashtable @{Id=1000} -MaxEvents 20 |
  Select-Object TimeCreated, @{n='Msg';e={$_.Message}} | Format-List
```

事件 1000 会直接给：`Faulting application name` / `Faulting module name` / `Faulting module version` / `Exception code 0xc0000005` / `Fault offset`。
**这一步就决定后续一切**：
- 落在 `libmpv-2.dll` → H1/H6 主线；
- 落在 `flutter_windows.dll` / `d3d11.dll` / `dxgi.dll` → H3；
- 落在 `amdxx64.dll` / `amdxc64.dll` → H5（驱动）；
- 落在 `aushd*.exe`（自家 runner）→ 我们自己的代码，反查 `video_host`/`native_window`。

同时读两台机器的 mpv 版本，排除 H6：

```powershell
Get-ChildItem "$env:APPDATA\AusHD\AusHD Player\logs" | Sort-Object LastWriteTime -Desc | Select -First 20
# 日志里搜 'mpv' 版本行 / VO 行 / gpu-api 行
Select-String -Path "$env:APPDATA\AusHD\AusHD Player\logs\*.log" -Pattern 'VO:|gpu-api|gpu-context|vulkan|d3d11|mpv ' -Encoding Unicode
```

### 5.2 系统侧事实（先看有没有 TDR）

```powershell
Get-WinEvent -LogName System -MaxEvents 500 |
  Where-Object { $_.Id -in 4101,41,4102 -or $_.ProviderName -match 'amd|display|Kernel-Power' } |
  Select-Object TimeCreated, Id, ProviderName, @{n='M';e={$_.Message.Substring(0,[Math]::Min(200,$_.Message.Length))}}
```

- `4101`（Display driver stopped responding and has successfully recovered）= TDR → H5。
- `Kernel-Power 41` = 整机掉电/硬挂，通常意味着比 AV 更糟的情况。
- 完全没有 → 进程自己崩的，回到 H1/H3。

### 5.3 让 Windows 自己写全量 dump（零代码，改注册表）

```powershell
$exe = 'aushd_player.exe'   # 以 installer/zerk_play.iss 里实际 exe 名为准，常见别名各建一份
$base = "HKLM:\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\$exe"
New-Item -Path $base -Force | Out-Null
New-ItemProperty -Path $base -Name DumpFolder -PropertyType ExpandString -Value 'C:\CrashDumps' -Force
New-ItemProperty -Path $base -Name DumpType   -PropertyType DWord        -Value 2          -Force  # 0=mini 1=mini+ 2=full
New-ItemProperty -Path $base -Name DumpCount  -PropertyType DWord        -Value 20         -Force
```

前提：进程没有自己装一个"吞掉未处理异常并静默退出"的 filter（本仓库没有 `SetUnhandledExceptionFilter`，符合）。
`DumpType=2` 是全量 dump，几十 MB～几百 MB，能看完整线程栈、堆和模块列表。

### 5.4 抓 first-chance（比二次访问违例更有信息量）

```powershell
procdump64.exe -accepteula -ma -e 1 -n 20 -x C:\CrashDumps aushd_player.exe
```

`-e 1` = 每个 first-chance 异常都 dump（驱动把错误转成异常的那一刻就能抓到，早于最终 AV）；`-t` = 进程终止时再 dump 一份。
带 `-w` 可以驻留等待进程启动。

### 5.6 mpv 侧日志：现在等于没开

`lib/playback/mpv/mpv_options.dart:60` 硬编码 `msg-level=ffmpeg=error`，把 `vo`/`gpu`/`vulkan`/`libplacebo` 的输出全关了。诊断构建请改成：

并且在 app 日志里**固定记录一次渲染路径快照**（当前日志没有，所以第 16:55 那次的 `VO: [gpu]` 让人误判成 gpu-next）：

### 5.7 dump 分析配方

```powershell
cdb -z C:\CrashDumps\aushd-crash-*.dmp -c ".symfix; .reload; !analyze -v; lm; ~*kb; q"
```

判读要点：

1. `!analyze -v` 的 `MODULE_NAME` / `IMAGE_NAME` / `FAILURE_BUCKET_ID` → 先定模块（和 §5.1 交叉验证）。
2. **execute @ 0x0**：`kb` 里 `RIP=0` 的那一帧，其**返回地址**就是"谁发起了这个虚调用" —— 这是最有价值的一行。
3. **read @ 0x24**：`kb` 找基址为 0 / 很小的那一帧，看是 `this` 还是某个结构体字段；`!address 0x24` 没意义，要反汇编那几行看偏移。
4. 两个 dump 若是**不同模块**，说明是两件事，别当同一个 bug 修。
5. 把 dump 时间与 mpv/app 日志行对齐（`MINIDUMP_MISC_INFO` 里有进程启动时间 + 崩溃时间），才能回答"崩溃前最后一条 mpv 日志是什么"。

### 5.8 符号：三个模块各自的现状

| 模块 | 有没有符号 | 方案 |
|---|---|---|
| 自家 `aushd_player.exe` + runner | 现在 CI 只打 installer，**pdb 没归档** | 构建产物里带上 pdb 并归档 |
| `flutter_windows.dll` | 公开符号服务器有 | `_NT_SYMBOL_PATH=srv*C:\sym*https://msdl.microsoft.com/download/symbols` + Flutter 对应 engine 版本的符号包 |
| `libmpv-2.dll` | **没有公开 pdb** | 两条路：①在 CI 里用同 commit 自建带 `/Zi` 的 libmpv 并留 pdb；②退一步，用"模块+偏移"对照 mpv 源码手算。**这也是"pin mpv 版本"的第二个理由** |

## 6. 建议的执行顺序（半天内出结论）

| 步骤 | 成本 | 产出 |
|---|---|---|
| 1. §5.1 事件 1000 + §5.2 事件 4101 | 5 min | **faulting module** + 有无 TDR → 直接砍掉一半假设 |
| 2. 两台机器 `mpv-version` 对比 | 5 min | 排除/确认 H6 |
| 3. §5.3 装 WER LocalDumps，跑一次复现 | 15 min | 全量 dump（比现有 mini dump 信息多一个量级） |
| 4. §6 E3 对照（`gpu-api=opengl`）复现 10 次 | 15 min | 是"窗口 resize 本身"还是"具体 context" |
| 5. §6 E1/E2 对照 + `target-colorspace-hint=no` | 30 min | 定位最脆的那一环 |
| 6. 空窗全屏 10 次（不播放） | 5 min | 二分 Flutter/ANGLE vs mpv |
| 7. 按 §4.1 B 组合作为默认值发一个测试构建 | — | 用户可用性回归 |

第 1、3 步之后，根因基本就能定到"哪个模块 + 哪个线程"。第 4–6 步是把它压到一个具体的触发条件上。

## 7. 明确不建议的事

1. **不要继续在 `SWP_FRAMECHANGED` 这类窗口 flag 上试**（§3.1，已经被证明是伪变量）。
2. **不要再用"进程隔离 mpv"这条路**（v1.0.12 证伪：OSD 全丢，用户已放弃）。若将来要重做，正确姿势是 render API + 进程外解码/进程内渲染，而不是整段 UI 外移。
3. **不要在没有 dump 的情况下再改渲染参数发版**。现在的失败循环是"猜一个参数 → 发版 → 用户崩 → 回退"，成本全在用户身上。
4. **不要把 `hwdec` 和 `gpu-api` 一起改**：两个变量同时动，崩了也不知道是谁。

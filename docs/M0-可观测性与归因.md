> 对应 `docs/全屏崩溃-解决方案v1.md` §4.3 与 §5 的 M0。

## 1. mpv 日志：从"全关"到"只关 ffmpeg"

原来是：

```dart
'msg-level': 'ffmpeg=error',
```

这一行把 `vo/gpu`、`vo/gpu-next`、`vulkan`、`libplacebo` 的输出整体掐掉了。而三份 dump 里唯一能定位"销毁时驱动还在用什么"的证据恰好就在这些行里（例如 `[v][vo/gpu/win32] uninit` 之后 70–90ms 才崩）。现在：

```dart
'msg-level': 'all=info,vo=v,vd=v,ao=v,ffmpeg=warn',
```

同时把 mpv 日志从"只有用户手动打开详细日志才写"改成**总是写**，路径 `AppLog.sidePath('mpv')`，并只保留最近两个会话（第三个及更早的直接删），所以磁盘占用有上界。

## 2. 每会话模式快照

每次 `open()` 写一行 `[session]`：

```
[session] mode vo=gpu-next api=vulkan context=winvk hwdec=d3d11va flip=n/a
          fullscreen=true hdr=on display=2880x1800@120.00Hz scale=2.0 mpvLog=mpv-....log
```

为什么必须有它：三次崩溃对应三个不同构建，而**当时的渲染模式只能靠猜**。RenderGuard 会改 `gpuApi`、播放结束会 fire-and-forget 地改 HDR、全屏状态会泄漏——四个变量叠在一起，dump 无法归因。现在 dump 只要和同一时刻的 `[session]` 行挂钩，就能回答"崩的时候到底在跑哪条路径"。

`resolveMpvMode()` 被抽成 `MpvMode` 单一实现，options 表和日志行共用它，不会出现"日志说的和实际跑的不是一回事"。

## 3. WER dumps

`tools/wer-localdumps.ps1`（需管理员）：

```powershell
powershell -ExecutionPolicy Bypass -File tools\wer-localdumps.ps1            # 默认 D:\crashdumps，全量 dump，保留 5 份
powershell -ExecutionPolicy Bypass -File tools\wer-localdumps.ps1 -Undo      # 关掉
```

它写的是 `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\zerk_play.exe`：`DumpFolder=D:\crashdumps`、`DumpType=2`（全量）、`DumpCount=5`。

- 为什么不用进程内自写：崩溃在驱动 worker 线程里，进程内写 dump 时其它线程没有挂起，且实际是在故障数秒后才落盘（上次那份 dump 写完后 mpv 日志还继续写了 30 秒，把现场污染了）。
- 为什么放 D 盘：C 盘只剩约 2GB，一份全量 dump 就是几百 MB。
- 配套取证据：`Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000} -MaxEvents 5` 先拿 faulting module，再 `cdb -z <dmp> -c ".exr -1; !analyze -v; lm; ~*kb; q"`。

## 4. 版本 pin

| 项 | 改前 | 改后 | 为什么 |
| --- | --- | --- | --- |
| Flutter | `channel: stable`（浮动） | `flutter-version: '3.50.0'`（4 处） | 三次崩溃对应三个不同引擎构建，`TimeDateStamp` 各不相同，"同代码不同产物"本身就是待排除的变量 |
| libmpv | `releases/latest` | `releases/tags/20261111` | 同一个 mpv 版本的不同日期构建会装进不同的 `mpv.exe`/FFmpeg dll；而且这个 tag 编译出的正是崩溃日志里那句 `v0.42.0-38-gbcde6b93c` |

pin 的代价是更新要手动改一行；收益是任何一份 dump 都能对应到确定的二进制。

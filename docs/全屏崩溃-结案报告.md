# 全屏崩溃结案报告

2026-11-19

## 0. 一句话

不是某个渲染后端有 bug，是两件不同的事叠在一起：**全屏时切换显示刷新率**（`ChangeDisplaySettingsEx`）把驱动正在用的表面全部掀掉，以及**关停时释放对象的速度快于驱动队列排空的速度**。前者修在 m4，后者修在 m5；真机实测通过。

## 1. 两份独立的故障，曾被当成一份

三份 11-17 的 minidump 被 HANDOVER 当成同一件事，并且把栈上的返回地址误读成 faulting PC（`amdxx64+0x124815` 是**栈帧**，不是崩溃点），于是 1.0.9 去掉了 `SWP_FRAMECHANGED`，修的是一个不存在的落点。

真机上（11-18，同一个二进制，五次崩溃）才看清楚：

| 时间 | 后端 | 崩溃点 | 说明 |
|---|---|---|---|
| 11:44:19 | opengl/win + hwdec=no | `rip=0x0`，`amdxx64+0x124815` 栈 | 触发点正是全屏切换那一刻（mpv 日志 t+70s 与 WER 时间对齐） |
| 11:50:17 | d3d11（FL 12_1） | module unknown | 播放 16s |
| 11:52:53 | vulkan/winvk | module unknown | 播放 93s |
| 11:55:01 | vulkan/winvk | `flutter_windows.dll+0x1eaa0` | `[vo/gpu/win32] uninit` 之后 |
| 11:55:24 | 同进程 | `0xc000041d` 同偏移 | 崩溃处理自己制造的第二现场 |

**三种后端全崩**，所以"换后端"从来不是变量。共同点是当时会话里都有显示模式切换：加载时 120→75 Hz，退出时 75→120 Hz，而 11:55 那次崩在恢复桌面刷新率之后 5 秒、落在 ANGLE（`flutter_windows.dll`）里。

## 2. 全屏族：显示模式切换（m4 修）

证据链：

1. 三种 GPU 后端 × 五个 dump，崩在同一个 AMD 用户态驱动 worker（`BaseThreadInitThunk` 起，`amdxx64+0x124815 ← +0x1249b9 ← +0xfd7c7f`）。
2. 11:55 的 dump 崩在 `flutter_windows.dll`——那是 ANGLE，不是 mpv；两个模块同时崩，说明被掀掉的是**驱动持有的所有表面**，不止视频那一个。
3. `[refresh] switched to 75 Hz` / `[display] restoring the desktop refresh rate` 是当时唯一会整体失效表面的动作（这台机器 15 个显示输出、200% DPI、2880x1800@120Hz）。

修复：`DisplayRefreshMatcher.modeSwitchingEnabled = false`，应用不再调用 `ChangeDisplaySettingsEx`，进入/退出播放都留在桌面刷新率。

真机结果（4K HEVC 10bit HDR10，3840x1600@60fps）：

```
enter ok in 162 / 296 / 277 / 186 / 210 ms
exit  ok in 265 / 163 / 141 / 127 / 182 ms
```

10 次进出全过，零崩溃。**这是本项目第一次在真机上通过全屏切换。**

代价（必须写明）：**"匹配视频刷新率"这个功能当前是关闭的**。设置界面里的 `matchHz` 开关已不起作用，后续要么隐藏它，要么改成"只在 VO 尚未创建时切换一次、退出前不切回"的安全版本。

## 3. 返回键族：关停队列没排空（m5 修）

m4 之后全屏不崩了，但点左上角返回会偶发卡死。日志显示关停链**完全正确**：

```
[ session] finish (userExit)
[session] close start (vo-configured=yes)
[video_host] hidden
[mpv] quit sent
[mpv] shutdown event received
[refresh] restored
[session] close done
[session] player closed
```

然后 6 秒后 WER 记录访问违规，而进程仍在写日志——一条线程死了，UI 再也回不来，所以用户看到的是"卡死"而不是"闪退"。

两份 dump（13:17:55 与 13:19:39）两种崩法、同一条栈：

| rip | params | 含义 |
|---|---|---|
| `amdxx64+0x1015610` | `[0x0, -1]` | 驱动内部读了 `-1` |
| `0x0` | `[8, 0]` | 驱动调了空函数指针 |

修复（`lib/playback/mpv/mpv_backend.dart`）：拆之前先 `pause=yes` 停 250 ms 再 `stop`；stop → hide → quit 的停等 150 → 400 ms；`vo-configured` 等待 250 → 600 ms；新增 `[mpv] destroyed` 与 `[session] close done in <n> ms` 两条锚点。

真机结果：连续"进播放→立刻返回"多次，不再卡死。

## 4. 顺带修掉的东西

| 问题 | 位置 | 修法 |
|---|---|---|
| 模式记忆从未生效（日志说避开 vulkan，实际又用 vulkan） | `lib/playback/mpv/mpv_options.dart` | `effectiveHwdec()` 成为唯一来源（此前比对用 `settings.hwdec`，记录用 `options['hwdec']=auto-safe`，永不相等） |
| 旧守卫写进配置的毒（`steps:9`、`opengl+hwdec=no`）被当成手动选择 | `lib/playback/render_guard.dart` | 以退役键 `flutter.render.guard.v1` 为证据迁移一次到 `d3d11/gpu/d3d11va`，然后删键 |
| 崩溃那次的日志整份丢失 | `lib/core/log/app_log.dart` | 每秒 flush |
| `[fullscreen] enter ok after 47557 ms` | `lib/core/windows/fullscreen_controller.dart` | 改成真实耗时（原数字是进程启动至今） |
| 窗口层：`WM_SIZE` 不判最小化、每次 resize 重建 mpv 交换链、`OnDestroy` 至少两次、`WM_FONTCHANGE` 无空判 | `windows/runner/*` | m1 逐项修（见 `docs/M1-窗口层改造记录.md`） |
| 全屏两套权威各说各话 | `lib/core/windows/fullscreen_controller.dart` | 单一 FSM + 串行队列 + 超时 + 以原生态为准 |

## 5. 云端闸门（回归用）

- `.github/workflows/window-soak.yml`：`--window-soak` 全屏 soak，40 轮（PR 级）与 200 轮（`long_run`）。
  最近一次 200 轮：`wmSize=659 transitions=440`（比值 1.50，与 40 轮一致 → 自激 resize 被闸住）、`worst=51 ms`、`PASS violations=0`。
- `.github/workflows/build.yml`：Linux 上 `flutter analyze` + 全部单测（含 7 个 `FullscreenController` 用例）+ 三平台构建。

**边界**：托管 runner 没有 AMD GPU，`amdxx64` 那次崩溃永远不可能在云端复现。云端只能证明"窗口层没回归"，不能证明崩溃已修；崩溃是在真机上、用同一个二进制跑出来的。

## 6. 仍然存在的问题（不收工的部分）

1. `matchHz` 功能被禁用，UI 上的开关需要处理（隐藏或改安全实现）。
2. 驱动 worker 的崩溃是**被推迟**而不是被消灭：m5 靠"先停帧、再排空"把窗口躲开。如果将来在更重的码流（8K、AV1）上复现，下一个手段是**进程隔离**（mpv 跑在子进程，崩了只丢一路视频，UI 重启播放器），而不是继续调 API。
3. 目标验收里要求的"30 分钟 4K HDR 全程 + 200 次全屏 + 无新增 dump"还没做完整长跑，目前通过的是"多轮进出 + 连续返回"。

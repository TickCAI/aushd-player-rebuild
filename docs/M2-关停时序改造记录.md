# M2 落地记录：关停时序（2026-11-18）

> 对应 `docs/全屏崩溃-解决方案v1.md` §3.1 与 §5 的 M2。
> 分支 `ci/m2`，commit `32c7f01`。

## 0. 这一版要解决的是"拆的顺序"，不是"用哪个渲染器"

三份 dump 里有两份（`…130037`、`…142636`）的崩溃时刻是确定的：

- mpv 日志写到 `[v][vo/gpu/win32] uninit`（VO 开始卸载）；
- **70–90 ms 之后**故障落在一个由 AMD 驱动自己创建的 worker 线程上（栈底 `kernel32!BaseThreadInitThunk`），faulting 指令是 `INC dword ptr [rax+24]`，`RAX=0`；
- 当时的命令行正是 RenderGuard 的降级档（`--vo=gpu --gpu-api=opengl --gpu-context=win --hwdec=no`）。

也就是说：**不是渲染器选错了，是 VO 已经在卸载、驱动还在用它，而我们同时把窗口、显示模式、Dart 侧对象一起拆了。**

## 1. 改造前的关停顺序

```dart
close() {
  _refresh.restore();      // ① 先改显示器刷新率/模式
  await _sub?.cancel();
  VideoHost.onInput = null;
  await VideoHost.hide();  // ② 立刻隐藏视频宿主
  _mpv.dispose();          // ③ terminateDestroy：阻塞 UI 线程，join mpv 线程
  ...
}
```

加上 `_finish()` 里的两行 `unawaited(NativeWindow.setHdr(false))` / `unawaited(DisplayGuard.clear())`，实际发生的是：**mpv 的 VO 卸载、Flutter 的 ANGLE 表面销毁、显示模式切换，三条路径在同一时刻并发跑在同一个驱动上**。`terminateDestroy` 本身会 join mpv 线程，而 VO 线程此时还在释放 GPU 对象——那 70–90 ms 就是 join 卡住的窗口。

## 2. 改造后的顺序（每一步都有日志锚点）

| # | 动作 | 日志锚点 | 为什么必须在这一步 |
| --- | --- | --- | --- |
| 0 | `close()` 幂等闸门 | `[mpv] close() re-entered; ignoring` | ESC / 房间 / 崩溃恢复三个路径可能在同一帧都调进来 |
| 1 | 停事件订阅、摘 state 监听、`VideoHost.onInput=null`、`Gamepad.playerSink=null` | `[session] close start (vo-configured=…)` | 先断掉"拆解过程本身产生的事件"回流，否则 OSD 回调会把播放器重新拉起来 |
| 2 | `command(['stop'])`，轮询 `vo-configured` 直到 false（最多 250 ms） | `[vo] quiesced vo-configured=false (reached / kept open by keep-open)` | 让 VO 自己停止呈现，而不是被我们抢走设备。`keep-open` 会把 VO 留在最后一帧，所以超时是**预期**，如实记录而不是假装成功 |
| 3 | 停留 150 ms，再 `VideoHost.hide()` | `[video_host] hidden` | 150 ms 在 24 Hz 也覆盖一帧以上；先停呈现再隐藏子窗口，避免隐藏瞬间触发 swapchain 释放 |
| 4 | 再停留 150 ms，然后 `command(['quit'])` 并等 `MPV_EVENT_SHUTDOWN`（最多 3 s） | `[mpv] quit sent` / `[mpv] shutdown event received / TIMEOUT` | **这是关键一步**：mpv 在自己的线程里把 VO、GPU 设备按它的顺序释放，并主动告知完成。之后 `terminateDestroy` 只是释放 handle，没有活着的核心可 join |
| 5 | `terminateDestroy` | — | 必须调用（否则 handle 泄漏），但此时已经没有并发的 VO 卸载 |
| 6 | 恢复刷新率（或 `keep()`） | `[refresh] restored` | 显示模式切换会强制重建所有表面；放在 mpv 之后，才不会和 VO 卸载抢同一个设备 |
| 7 | 回到 Dart：`await NativeWindow.setHdr(false)` → `await DisplayGuard.clear()` | `[session] player closed` → `[hdr] restored off (ok/failed)` | 原来这两行是 `unawaited`，现在串在关停之后，异常也能被看到 |
| 8 | 收尾 | `[session] close done` | 与 `[session] finish` 配对，日志里能直接读出整条链是否有序 |

## 3. 顺带修掉的三处"让故障看起来像崩溃"的坑

1. **事件泵会被一个抛异常的监听者打死**（`mpv_player.dart` 的 `_drain`）。`_events` 是 `StreamController.broadcast(sync: true)`，任一监听者抛异常就会中断 `while` 循环——本批剩余事件全丢。丢掉 `MPV_EVENT_SHUTDOWN` 会让上面的第 4 步直接超时；丢掉 `end-file` 会让进度条冻在结尾。现在每个事件单独 `try/catch` 并打印，泵不再死。
2. **`osd()` 会打到已 dispose 的 `_curtain`**。`_curtain.dispose()` 在 `close()` 末尾，此后任何 OSD 相位变化都会在 `ChangeNotifier` 上抛异常——正好命中第 1 条。现在 `osd()` 与 `_showVideo()` 都以 `_closed` 闸门挡在前面。
3. **`_showVideo()` 可能在关停中途把视频宿主重新显示出来**，等于在拆除路径上重建一次交换链。同样被 `_closed` 拦住。

## 4. 云端能证到什么、不能证到什么

**能证**（[run 44225464572](https://github.com/TickCAI/aushd-player-rebuild/actions/runs/44225464572)，`32c7f01`）：`flutter analyze` 0 error、Windows release 构建通过、M1 的 40 轮窗口 soak 仍然全绿（没有回归）。

**不能证**：soak 模式不创建 video host、也不创建 `MpvPlayer`（云端不装 libmpv），所以上面这张表里**没有任何一步被运行时执行过**。M2 的正确性目前只有代码论证，没有实测。

## 5. L3 清单（需要一台有 AMD 显卡的机器，一次完整会话）

1. 以管理员跑一次 `tools/wer-localdumps.ps1`（M0 遗留项）。
2. 跑一次播放 → ESC 退出，然后 `%LOCALAPPDATA%` 下的应用日志里应当出现下面这条**严格有序**的链：
   `[session] finish` → `[session] close start` → `[vo] quiesced` → `[video_host] hidden` → `[mpv] quit sent` → `[mpv] shutdown event received` → `[refresh] restored` → `[session] player closed` → `[hdr] restored off` → `[session] close done`
3. 若中途出现 `shutdown event TIMEOUT`，说明 mpv 拒绝退出（通常是脚本或 IPC 卡住），把该会话的 `mpv-*.log` 一起发过来——现在它是常开的。
4. 播放 4K HDR10 片段 30 分钟、期间进出全屏 200 次；判定失败的条件只有一个：**新增 `*.dmp` 或 Application Error 1000/1001 事件**。
5. 每条 `[session]` 行都会带上当时的 `vo/api/context/hwdec/flip/fullscreen/hdr/display`，dump 与它配对即可确认"崩的时候在跑哪条路径"。

## 6. 还没做的（留给 M3）

- `_play()` 仍是 `unawaited`，`_finishing` 只在开头查一次：关停后 `_play` 可能继续 `load`/`selectTrack`，现在被 `MpvPlayer._disposed` 静默吞掉——**掩盖**而不是修复。
- OSD 相位仍在 show/hide 视频宿主（§3.4 的帧抖动源）。
- RenderGuard 仍会把 `gpuApi` 写进用户配置（§3.5）。
- `test/` 目录仍无 `FullscreenController` 单测（§4.3 的 T3）。

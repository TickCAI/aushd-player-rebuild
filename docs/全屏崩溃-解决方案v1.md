# 全屏崩溃解决方案 v1

> 项目：`aushd-player-rebuild`（Flutter + libmpv，Windows 主战场）
> 依据：三份 minidump 硬证据 + 三份专家分析（高级开发者 / 代码审查工程师 / 桌面应用工程师）
> 验证方式：GitHub 云端 CI，不做本机实测
> 状态：**方案**（本轮只落地"验证骨架"，不改修复性代码）

---

## 0. 一页结论

**不是某个渲染器有 bug，是驱动还在用这块显存的时候，我们把窗口、显示模式、GL 上下文一起拆了。**

三条硬证据：

| 证据 | 内容 | 它排除了什么 |
|---|---|---|
| 崩溃线程归属 | 三次崩溃都落在 `amdxx64` 自己起的 worker 线程（栈底 `kernel32!BaseThreadInitThunk`） | 不是 Dart 线程、不是 mpv VO 线程、不是我们的代码崩的 |
| 崩溃指令 | 11:19 是 `faulting PC = 0x0`（`C0000005` execute，params `[8,0]` = **call null**）；13:00/14:26 是 `INC dword ptr [rax+24]` 且 `RAX=0`（**读已释放/未初始化堆块**） | 同一类"对象提前失效"，不同落点 |
| 崩溃时序 | 13:00/14:26 发生在 mpv 日志 `[v][vo/gpu/win32] uninit` 之后 **70–90 ms**，即 `mpv_terminate_destroy` 内部或紧后 | 崩溃点在**销毁路径**，不在渲染路径 |

于是十几版修不好的原因也就清楚了（三条系统性错误，见 §2）：一直改在"不是崩溃点"的地方，而且**从没有一个稳定二进制跑够次数做过对照**。

### 修复策略（一句话版）

把"拆的顺序"变成**有闸门、可等待、可验证的时序**（P0），把"崩溃"从"进程半死"变成"可恢复事件"（P1），最后再把渲染路径收干净（M3 架构）。**先能证伪，再谈修好。**

### 本轮已交付（代码已进仓库，等云端编译验证）

| 文件 | 作用 |
|---|---|
| `lib/dev/window_soak.dart` | 全屏 soak 驱动器：**只驱动窗口层**，无 mpv / 无网络 / 无鉴权，release 也能跑 |
| `lib/main.dart` | soak 入口（`AUSHD_WINDOW_SOAK=<n>` 环境变量，`AppServices.create()` 之前分流） |

## 1. 证据链：能证明什么，不能证明什么

### 1.1 三份 dump 的事实

| dump | 大小 / 模块 / 线程 | faulting PC | 栈（自内向外） | 场景 |
|---|---|---|---|---|
| `aushd-crash-20261117-111942.dmp` | 3.9 MB / 128 / 111 | **0x0**（execute AV） | `amdxx64+0x124815` → `+0x1249B9` → `+0xFD7C7F` | 播放中（107.6 s，`ao/wasapi` Under-run，`vo/gpu-next` + libplacebo + amdvlk64） |
| `…130037.dmp` | 1.2 MB / 97 / 40 | `ntdll+0xAA83` | `amdxx64+0x95E25` → `+0xA27E8` → `ntdll+0xC5FF` → `+0xD872` → `amdxx64+0xBE3FD` → `+0x124815` … | `uninit` 之后 70–90 ms |
| `…142636.dmp` | 同上（完全同构） | 同上 | 同上 | 同上 |

### 1.2 一个必须纠正的历史误读

`HANDOVER` 把栈上的 `amdxx64+0x124815` 当成 faulting PC，由此推出"`SWP_FRAMECHANGED` 触发帧重算打爆驱动"，v1.0.9 专门去掉了 `SWP_FRAMECHANGED` —— **这条路修的是一个不存在的落点**。该误读已固化进注释 `windows/runner/native_window.cpp:112-121`。

三条反证：

1. `0x124815` 出现在三份 dump 里状态不同：11:19 是 `[rsp]` 的首个返回地址，13:00/14:26 在同一位置但更外层还有 `+0xBE3FD`。
2. 13:00/14:26 的 faulting PC 明确是 `ntdll`（`FF 40 24` = `INC [rax+24]`，`rax=0`），不是任何 `amdxx64+0x…` 地址。
3. `C0000005` 的 `ExceptionInformation[0]=0` 表示**读**，`[1]=0` 表示访问地址 0；execute AV 的 `[0]=8`。两次形态不同，说明是两条路径。

### 1.3 大概率是两个 bug，不是同一个

| | 11:19 | 13:00 / 14:26 |
|---|---|---|
| 进程内有没有 libmpv | **有**（mpv 在主进程内渲染） | **没有**（mpv 已进程隔离 + `--wid` 嵌入） |
| 崩溃时机 | 播放中，`vo/gpu-next` + Vulkan | `terminate_destroy` 内部/紧后 |
| 触发方 | libmpv/ANGLE 侧表面销毁 | 父进程侧表面销毁 / 跨进程 HWND 操作 |
| 共同点 | 都落在同一条 UMD worker 上（`0x124815` 是公共入口） | 同左 |

**结论**：任何"只改一处"的修法都只能消掉其中一个，另一个会继续在以另一种形态出现 —— 这就是"十几版反复失败"的物理原因。

### 1.4 不能证明的部分（诚实边界）

- 没有 AMD 驱动符号表，`amdxx64+0x…` 无法落到函数名；
- 三份 dump 的 `zerk_play.exe` TimeDateStamp 分别是 11:10:24 / 12:50:21 / 13:14:32 = **三个不同构建**，从未有稳定二进制跑够次数；
- dump 是进程内自写 `MiniDumpNormal`（不挂起其它线程），崩溃后进程还活着 76 s，`mpv_log` 末尾 30 s 记录的是**崩溃之后**用户晃鼠标；
- 仓库全历史 `git log --all -S MiniDumpWriteDump` 为空 → 那三份 dump 是 WER/外部工具产物，当前没有自建崩溃处理器。

## 2. 为什么前面十几版都没修好

| # | 系统性错误 | 具体表现 | v1 的对策 |
|---|---|---|---|
| 1 | **改在不是崩溃点的地方** | `SWP_FRAMECHANGED` 白删；`RenderGuard` 降档方向在 Windows 上是反的（vulkan 不是"更安全"），还把崩溃从播放中挪到关停时 | §3 的改动全部带 file:line 和"它对应哪条证据" |
| 2 | **没有稳定二进制** | 三个构建 vs 三次崩溃，无法归因 | M1 起每个改动一次 CI 构建、一个 tag、一份 dump 对照 |
| 3 | **没有可观测性** | `msg-level=ffmpeg=error` 把 vo/gpu/vulkan/libplacebo 全关；`player_smoke.dart:12` 在 release 直接 `return`；没有诊断通道；`test/` 8 个文件无一触及窗口/全屏 | §4 云端 soak + 关停序列断言 + 事件泵活性 + 失败自动抓事件日志 |
| 4 | **崩溃处理把事故变半死** | 进程内写 dump、不死线程继续跑 30 s、下一次启动只看到"上次崩了"就降档 | P1：看门狗 + 进程隔离，把 crash 变 restart |

**所以 v1 的前两个里程碑不是修 bug，而是"可证伪"和"可归因"。** 没有这两步，第 N+1 版和第 N 版没有区别。

## 3. 修复设计

分三级：P0 = 直接参与崩溃窗口的时序/生命周期；P1 = 竞态与状态权威；P2 = 让故障可归因。每条都标注"对应证据"。

### 3.1 P0-1 关停时序：先 quiesce，再 destroy

**对应证据**：13:00/14:26 崩在 `uninit` 后 70–90 ms。
**现状**：`lib/playback/mpv/mpv_player.dart:246-255` `dispose()` 直接 `terminateDestroy()` —— **阻塞 UI 线程 join mpv 线程**，全程没有 `command('quit')` 等 `MPV_EVENT_SHUTDOWN` 的握手，而 `_drain` 明明处理了 `MpvEventId.shutdown`（说明当初就打算这么设计）。上游 `mpv_backend.dart:247-266` `close()` 是 `await VideoHost.hide()` 紧接 `_mpv.dispose()`，中间没有任何排空等待。

**改成有闸门的顺序**（每一步都有可观测的前置条件）：

```
1. stop（mpv "stop"）                    → 停止喂帧
2. 等 vo-configured == false             → VO 真的解绑了（轮询 property，200ms 粒度，2s 超时）
3. 等 >= 2 帧（frame-count 增量）         → UMD 队列至少排空两个 present 周期
4. VideoHost.hide()                      → 摘掉视频子窗口（此时已无 present）
5. 等 100–200 ms                          → 给 AMD 的延迟销毁队列一个窗口期
6. command('quit') + 等 MPV_EVENT_SHUTDOWN  → 让 mpv 自己走完 uninit
7. terminateDestroy()                     → 最后一步才是硬销毁
8. 关闭 events / 置空句柄
```

任一步超时：**记录并按当前状态继续**，但打 `[mpv] quiesce-timeout step=N`，绝不静默跳过。

**为什么这样能避开 UMD 异步队列**：崩溃的本质是"驱动队列里还有引用，而引用指向的对象已经被释放"。1/2/3 步保证销毁时队列为空，5 步给了驱动内部延迟回收一个时间窗（这是唯一"经验性"的一步，所以它必须是**可观测**的，不能黑盒 sleep）。

**同一处必须一起改的三件事**：

- `lib/playback/playback_session.dart:952-961` `_finish()` 由 ESC→OSD `'back'` 同步路径 `unawaited` 出来 → 必须改成可 await 的单一收尾，且加 `_finishing` 幂等闸门（现在 `:227` 只查一次）。
- `_finish` 里 `unawaited(NativeWindow.setHdr(false))` → 改成"收尾序列的最后一步，且 await"（现在是在播放器销毁之后 fire-and-forget 改全局显示模式）。
- `lib/playback/display_refresh.dart:74` 的恢复在 `MpvBackend.close()` **最前面**（先复位显示模式再销毁 mpv）→ 必须移到 mpv 完全销毁**之后**。显示模式变化会让 D3D/GL 交换链重建，跟销毁撞一起就是双杀。

### 3.2 P0-2 窗口层闸门：别在错误的时刻动别人的窗口

**对应证据**：11:19 的 `call null`；`OnParentResized` 跨线程同步改 mpv 的 VO 子窗口。

| 文件:行 | 现状 | 改成 |
|---|---|---|
| `windows/runner/video_host.cpp:135-143` | `MoveWindow(hwnd_)` 后对 `GetWindow(GW_CHILD)`（mpv 的 VO 子窗口）再 `MoveWindow(..., TRUE)`，同步 SendMessage 跨线程 | **删掉对 `GW_CHILD` 的移动**（VO 子窗口由 mpv 自己按父窗口客户区跟随）；必须保留时用 `FALSE`（不发 `WM_WINDOWPOSCHANGED` 环）+ `IsWindow` + vo-configured 判断 |
| `windows/runner/flutter_window.cpp:73-75` | 每个 `WM_SIZE` 都 resize，且发生在 `Win32Window::MessageHandler` 真正改 view 尺寸（`:84`）**之前** | resize 合并（80–120 ms 去抖）+ 延后到 view 尺寸确定之后 |
| `windows/runner/win32_window.cpp:179-186` | `WM_SIZE` 不判 `SIZE_MINIMIZED` → 最小化时 `MoveWindow` 成 0×0 | 加 `if (wparam == SIZE_MINIMIZED) break;`，且 0 尺寸直接跳过 |

0×0 尺寸是驱动最容易空解引用的状态之一（分配 0 大小的 swapchain 纹理），而最小化到任务栏是**日常操作**。

### 3.3 P0-3 `SetFullScreen` 重写：单一权威 + 样式往返

**对应证据**：`ROOT` 里 `SetFullScreen(false)` **全仓库无人调用**；三入口并发；`GetMonitorInfo` 失败时原生 no-op 但仍回 `Success()`。

| 问题 | 位置 | 修法 |
|---|---|---|
| 原生失败仍报成功 → Dart / mpv user-data / 原生三方状态不一致 | `native_window.cpp:83-102` vs `:123-124` / `:136` | 失败路径也写 `fullscreen_`，并且 `result->Success(false)` + 带错误码；Dart 侧不再盲信返回值，用 `isFullScreen()` 回读校验 |
| 改 `GWL_STYLE` 不发 `SWP_FRAMECHANGED` → 客户区填不满、`WM_NCCALCSIZE` 推迟到之后任意 resize | `:128` / `:133` | **恢复** `SWP_FRAMECHANGED`（1.0.9 删错了），但只在样式**真的变化**时发，且与 `SWP_NOSENDCHANGING` 一起用 |
| `SetWindowPos` 缺 `SWP_NOSENDCHANGING`，与 `WM_DPICHANGED`(`win32_window.cpp:169-178`) 构成无闸门环 | `:129-131` | 两处都补 `SWP_NOSENDCHANGING` |
| 退出只还原 style+placement，不还原最大化语义；与 `window_manager` 每次 `WM_GETMINMAXINFO` 强写 `ptMinTrackSize`（DPI 2.0 下 960×540 逻辑 = 1920×1080 物理）冲突 | `window_manager_plugin.cpp:190-205` | 全屏/退出**完全交给 window_manager 的同源实现**（`window_manager.cpp:575-654`），自己不再手改 `GWL_STYLE`；退出时显式重设 FlutterView 尺寸 |
| 三入口并发无 single-flight | `lib/core/windows/native_window.dart:24-27`；入口 `lib/main.dart:172`(F11)、`lib/main.dart:48`(启动)、`mpv_backend.dart:551-555`(OSD `send("fullscreen")`) | 抽 `FullscreenController`（纯 Dart，可单测）：`windowed→entering→fullscreen→exiting` FSM，带版本号 + 超时 + 过渡期丢弃对端事件 |
| 全屏状态永久泄漏（从没人 `setFullScreen(false)`） | 全局 | 退出播放/回列表必须显式复位，且 soak 里作为**硬断言** |

`lib/main.dart:46-49` 的启动全屏也要挪到首帧之后（现在跑在 `SetNextFrameCallback(Show)` 之前），否则首帧回调与全屏 `SetWindowPos` 抢同一个时序。

### 3.4 P1-1 OSD 相位不再 show/hide 视频宿主（真正该打的地方）

**对应证据**：`[jank] 380 ms frame, raster 283 ms`。

`mpv_backend.dart:210-223` / `:184-190`：`_showVideo(_curtain.phase == 'playing' && _framed)` 意味着**每次 OSD 相位变化就 `ShowWindow(SW_HIDE)` / `show()` 视频宿主** → 每次相位切换都在销毁/重建 mpv 的交换链。这才是真正的 frame churn，v1.0.9 打偏的那一枪本该打在这里。

改成：视频宿主生命周期与**播放会话**绑定（load 后 show、关停时 hide），OSD 相位只影响 OSD 自身的可见性（OSD 本来由 mpv 自己渲染）。

条带切歌/续播时同理：`loadfile replace` 不得重置 `_framed` / `_videoShown`（`mpv_backend.dart:221`、`:276`）。

### 3.5 P1-2 RenderGuard 改为"模式记忆"，别把原因写进用户配置

**对应证据**：`render_guard.dart:77-85` 三档降级 + `:71-74` `_steps` 永不因连续成功清零 + `playback_launcher.dart:60-68` 用**异常消息字符串** `/mpv|video host|gpu|vo=/i` 匹配 + `recoverOnStartup` 对任何崩溃类型都降档。

改成：

- sentinel 记录**出事时的完整模式** `{vo, gpu-api, hwdec, fullscreen, hdr, refresh}`，重启时**避开该组合**，而不是"往下踩一档"；
- 判据只看"mpv 是否启动失败"（日志 `[render-guard] mpv failed to start`），不看异常消息字符串；
- 连续 N 次成功 → 清零，回到默认（现在是永不回血）；
- 默认组合改为 `vo=gpu, gpu-api=d3d11, gpu-context=d3d11, d3d11-flip=no, hwdec=d3d11va`；`gpu-next`/`vulkan` 标 `experimental`，**移除自动降级**。

### 3.6 P2 让故障可归因（不修 bug，但决定下次能不能修）

## 4. 云端验证体系（本轮重点）

### 4.1 必须先说清楚的一条边界

**GitHub 托管的 `windows-latest` 没有 AMD GPU**（只有 Microsoft Basic Render Driver / WARP）。所以：

> **`amdxx64` 里那次崩溃，永远不可能在托管 runner 上复现。**

这条不写清楚，后面就会拿"CI 全绿"当"修好了"，然后第 N+2 版再翻车一次。云端能负责和不能负责的部分必须分开：

| 层 | 跑在哪 | 能证明什么 | 不能证明什么 | 成本 |
|---|---|---|---|---|
| **L0** 静态闸门 | `ubuntu-latest` | 编译、analyze、`FullscreenController` 单测（并发/超时/幂等） | 任何运行时行为 | ~3 min |
| **L1** 窗口 soak | `windows-latest`（无 GPU） | 双 resize、`SIZE_MINIMIZED`、样式往返、两个全屏权威不一致、全屏泄漏、帧停顿、进程存活 | 驱动崩溃（无 AMD 驱动） | ~12 min |
| **L2** 关停序列 | `windows-latest` | 日志严格有序、事件泵活性（`time-pos` 单调）、关停后无事件 | 同上 | ~15 min |
| **L3** 真机信号（可选） | **self-hosted runner，注册在 AMD 这台机器上** | 真驱动崩溃、真 dump、真 HDR/120 Hz | 需要机器开机（仍由云端调度，不是手动测试） | 按次 |

L3 是这套体系里唯一能碰到真问题的一层，而且它**仍然满足"不做本机手动实测"**：`workflow_dispatch` 从网页点一下，runner 自己拉起应用、跑 200 次全屏 + 播放、用 WER `LocalDumps` 抓 dump、上传 artifact、`mdmp.ps1` 解析。一个人都不用守着屏幕。

### 4.2 L1/L2 的判据（已实现，见 `window-soak.yml` + `lib/dev/window_soak.dart`）

soak **只驱动窗口层**：不建 mpv、不联网、不鉴权，所以它在 release 构建、在无 GPU 的 runner 上都能跑。每轮 = 进全屏 + 退全屏，逐轮断言：

| 断言 | 反的是哪个已知缺陷 |
|---|---|
| `zerk/window.isFullScreen()` 与 `window_manager.isFullScreen()` **必须一致** | 两个全屏权威各说各话（§3.3 第一行） |
| 全屏 bounds ≥ 窗口化 bounds，且退回后 ≤ 基线 | 客户区填不满 / 沉浸式窗口变小（`SWP_FRAMECHANGED` 缺失） |
| 每 10 轮并发 `toggleFullScreen()` ×3 不崩、不卡死 | 三入口并发无 single-flight（`native_window.dart:24-27`） |
| 结束必须 `isFullScreen() == false` | 全屏状态永久泄漏（`setFullScreen(false)` 无人调用） |
| 帧数 ≥ 轮次，p99 帧跨度 < 50 ms | 过渡期 raster 停顿（`[jank] 380 ms`） |
| 进程退出码 0 | 窗口层任何 AV/死锁（watchdog 240 s 兜底 exit 3） |

退出码语义：`0` 全过 / `1` 断言失败 / `2` soak 自身异常 / `3` 看门狗超时。CI 只看退出码，报告文件（`soak-report.txt`）作为 artifact 上传。

### 4.3 下一步要补进 L1/L2 的（M0 里程碑内容）

现在 soak 是用**现有** API 断言（已在仓库里、零原生改动）。M0 要补原生可观测性，把这些变成可断言的：

- 新增只读通道 `zerk/diag`：`clientRect` / `windowStyle(GWL_STYLE)` / `monitorRect` / `wmSizeCount` / `onParentResizedCount` / `videoHostVisible`；
- 断言"每次全屏切换 `wmSizeCount` 增量 ≤ 3"（现在是双 resize，增量会是 4–6）；
- 断言"样式往返 200 次逐位相等"（`WS_CAPTION|WS_THICKFRAME` 不漂移）；
- 断言"稳定播放中 `videoHostVisible` 不得翻转"（反 §3.4 的 show/hide churn）；
- 关停序列：`[session] finish` → `[mpv] quit sent` → `[mpv] shutdown event` → `[vo] uninit` → `[video_host] hidden` → `[refresh] restored` → `[hdr] restored`，严格有序；
- 事件泵活性：`time-pos` 每 500 ms 单调增长，关停后**不得**再收到任何 `MpvEvent`。

|---|---|---|---|

## 6. 验收标准（可自动断言，不靠人看）

1. `window-soak.yml`：40 轮（M1）与 200 轮（M2）退出码均为 0；
2. 全屏进入 250 ms 内有新帧，帧跨度 p99 < 50 ms；
3. 退出回列表后 `isFullScreen() == false` 且几何等于 `saved_placement_`；
4. 关停日志七步严格有序，关停后 0 个 `MpvEvent`；
5. `render_guard`：20 次连续成功会话后 `_steps == 0`；除非日志出现 `[render-guard] mpv failed to start`，否则**不得**改 `gpuApi`；
6. L3：30 分钟 / 200 轮 soak + 4K HDR 播放 0 异常退出、0 新增 `*.dmp`、WER 无 ID 1000；
7. `flutter analyze` 0 error，`flutter test` 全绿（含新增 `FullscreenController` 单测）。

## 7. 不做的事 / 风险

**不做**：

- 不动分发服务（`server/`）与更新器；
- 不把 A2 纹理方案作为修复手段（4K60 HDR 走 sw 必挂，先把 P0 做完再评估）；
- 不用"再降一档渲染器"当兜底（这是过去十几版的失败模式本身）。

**风险与兜底**：

| 风险 | 概率 | 兜底 |
|---|---|---|
| AMD 驱动侧真 bug（非我们能修） | 中 | 进程隔离 + 看门狗：崩溃 = 子进程重启，主 UI 不死；L3 持续采集直到能定位或上报 AMD |
| 托管 runner 无法复现真崩溃 → 误以为修好 | **高** | §4.1 的分层表 + 验收标准第 6 条强制要求 L3 一次通过才可发版 |
| `flutter` 未 pin 版本（`channel: stable`）导致"同代码不同产物" | 中 | M0 里 pin `flutter-version`，并把 `libmpv` pin 到具体 release tag + 归档 pdb |
| CI 分钟数成本 | 低 | 推送触发限定 `ci/**`、`soak/**`；long_run 只在手动勾选时跑 |
